## Java集合

### HashMap



#### 为什么 JDK 1.8 对 HashMap 进行了红黑树的改动？

这个问题的根本原因其实很单一：**JDK 1.8 要解决 HashMap 在极端情况下性能会从 O(1) 退化到 O(n) 的问题，而且这种退化在现实中并不是“理论上的小概率”**。

在 JDK 1.7 及以前，HashMap 的底层结构是数组加链表，hash 冲突发生时，所有落在同一个桶里的 key 都用单向链表串起来。在大多数情况下，只要 hash 分布足够均匀，这种结构是非常高效的，但它隐含了一个非常危险的前提：**你必须相信 hash 函数和 key 分布始终是“友好”的**。一旦出现大量 hash 冲突，同一个桶里的链表会变得很长，查找、插入、删除都要线性遍历，时间复杂度直接退化为 O(n)。

这个问题在早期更多被认为是“理论风险”，但随着 Web 应用和中间件的发展，它变成了一个现实问题。攻击者可以构造大量 hash 冲突的 key，刻意让 HashMap 的某些桶退化成超长链表，从而让一次普通的请求消耗大量 CPU，这类问题后来被归类为 Hash Collision DoS 攻击。也就是说，HashMap 的性能退化不只是“慢一点”，而是可能被恶意放大成系统级风险。

JDK 1.8 引入红黑树，本质上就是在**不放弃 HashMap 原有结构和使用方式的前提下，为最坏情况兜底**。当某个桶中的元素数量超过阈值（默认 8），并且整个数组容量已经达到一定大小（默认至少 64），这个桶就会从链表转换成红黑树。这样一来，即使所有 key 都落在同一个桶里，查找和更新的时间复杂度也能稳定在 O(log n)，不会再出现线性退化。反过来，当元素减少到一定程度（默认 6）时，又会退化回链表，避免在小数据量下引入树结构的额外开销。

这个设计并不是为了“让 HashMap 变得更快”，而是为了**让 HashMap 在最坏情况下不至于失控**。在正常 hash 分布下，链表依然是最轻量、最快的结构；只有在冲突严重、已经明显影响性能和安全时，才引入红黑树这种更重但更稳定的数据结构。换句话说，JDK 1.8 的这个改动是一次典型的工程权衡：**用一点实现复杂度和内存开销，换取在极端场景下的性能上界和系统安全性**。

### ConcurrentHashMap 

在 Java 7 中，ConcurrentHashMap 的核心目标是：**在保证线程安全的前提下，尽量降低锁冲突**，因此它采用的是分段锁设计。整个 Map 并不是一个整体，而是被拆成多个 Segment，每个 Segment 本质上是一个小型的 HashMap，同时继承了 ReentrantLock。线程在 put 或 remove 时，只需要锁住对应的 Segment，而不是整个 Map，这样多个线程只要操作落在不同的 Segment 上，就可以并发执行。读操作在大多数情况下甚至不需要加锁，而是依赖 volatile 保证可见性。这个设计在当时是非常先进的，但它有一个天然的限制：**并发度的上限等于 Segment 的数量**，而且 Segment 本身是一个较重的结构，锁粒度虽然比 Hashtable 小，但仍然是“粗粒度锁”。

到了 Java 8，ConcurrentHashMap 的设计思路发生了根本变化，目标变成了：**减少结构层级、进一步细化锁粒度、提升高并发下的伸缩性**。Java 8 彻底移除了 Segment 这一层结构，数据结构上更接近普通的 HashMap：一个 Node 数组加上链表或红黑树。并发控制不再依赖 ReentrantLock，而是主要使用 CAS 和 synchronized 的组合。写入时，先通过 CAS 尝试把新节点放入空桶，如果失败才在桶级别加 synchronized 锁，这个锁只作用于当前桶或树节点，而不是一大片数据；当链表过长时，还会像 HashMap 一样树化成红黑树，减少查询和更新的时间复杂度。读操作则完全无锁，通过 volatile 保证最新值可见。这种设计让锁的粒度从“段级”进一步缩小到了“桶级”，并发度不再受固定 Segment 数量限制，而是随着哈希分布自然扩展。

这种变化带来的结果非常明显：在 Java 7 中，ConcurrentHashMap 的并发性能更多取决于初始化时设定的 Segment 数量；而在 Java 8 中，并发性能更多取决于 key 的分布是否均匀。Java 8 的实现虽然在代码复杂度上更高，但减少了对象数量，降低了内存占用，同时在高并发、写多读多的场景下表现更好。也正因为 Java 8 使用了 synchronized 和 CAS 的配合，而不是显式的 ReentrantLock，它在 JVM 层面能获得更好的优化效果，比如偏向锁、轻量级锁和锁消除等。

## MySQL

### 存储引擎

#### MySQL 的存储引擎有哪些？它们之间有什么区别？

MySQL 的存储引擎本质上是**表级别的存储实现**，它决定了一张表的数据如何存、如何索引、如何加锁、如何做事务和崩溃恢复。MySQL 自身更像是一个“SQL 执行和调度层”，而真正的数据组织方式由存储引擎决定，因此不同引擎在能力和适用场景上差异很大。

InnoDB 是现在 MySQL 的默认存储引擎，也是绝大多数线上业务的首选。它的核心目标是**事务安全和并发能力**，因此实现了完整的 ACID 事务支持，包含 redo log、undo log、MVCC、多版本读以及行级锁。InnoDB 使用聚簇索引，数据和主键索引存储在一起，这让基于主键的查询非常高效，同时也决定了二级索引必须回表。为了应对宕机和异常，InnoDB 通过 WAL（先写日志再写数据页）保证崩溃恢复能力。这一整套设计使它非常适合高并发、强一致性、频繁写入的 OLTP 场景。

MyISAM 是 InnoDB 之前的主流引擎，它的设计目标是**简单和读性能优先**。它不支持事务、不支持行级锁，只能做到表级锁，因此在写入时会阻塞整张表，但在纯读或读多写少的场景下性能很好。MyISAM 的索引和数据是分开存储的，结构简单、空间利用率高，而且支持全文索引（早期 InnoDB 没有）。但正因为没有事务和崩溃恢复能力，一旦异常宕机容易导致表损坏，所以在现代生产系统中基本已经被淘汰，只在极少数只读或历史场景中使用。

Memory（也叫 Heap）存储引擎的核心特征是**数据完全存放在内存中**。它的读写速度非常快，但一旦 MySQL 重启，数据就会全部丢失。Memory 表默认使用哈希索引（也可以用 B+ 树），非常适合做临时数据、会话数据或中间结果缓存。它不支持事务，也不适合存放大数据量，因为数据直接占用内存，更多是作为一种“临时计算工具”存在。

Archive 存储引擎的目标非常明确：**高压缩、只写不改、用于归档**。它支持 insert 和 select，但不支持 update 和 delete，数据以压缩格式存储，占用磁盘空间非常小，适合日志、历史流水、审计数据等“写进去就不再动”的场景。它牺牲了查询和更新灵活性，换取极致的存储效率。

CSV 存储引擎是一种非常特殊的存在，它把表数据直接以 CSV 文件形式存储在磁盘上，设计目标是**与外部系统交换数据**。它不支持索引、不支持事务、性能也不高，但优点是格式通用，外部程序可以直接读写文件，适合做数据导入导出或简单的数据交换桥梁。

## Redis

### 持久化机制 

#### RDB

Redis 的 RDB 持久化本质上是**快照机制**，它做的是“在某一时刻，把整个内存中的数据状态完整地写到磁盘上”。当你触发 RDB 持久化时，Redis 会在内存里 fork 出一个子进程，父进程继续处理客户端请求，子进程在后台负责把内存数据序列化成 RDB 文件写入磁盘。这里的关键是 fork 后，操作系统通过写时复制（Copy-On-Write）技术保证父进程继续修改内存不会影响子进程生成的快照，也就是说，Redis 可以在不中断服务的情况下，把某个时间点的完整数据状态安全地写出去。序列化的过程本身非常紧凑，Redis 会将对象类型、键值对以及过期时间全部写入 RDB 文件，但它不会像 AOF 那样记录每一条写命令，而是直接把内存快照压缩成二进制存储，因此文件体积通常比内存数据小，写盘速度也快。RDB 的持久化触发方式可以是定时触发，也可以是手动触发，生成的文件可以用于备份或者主从同步，启动 Redis 时也可以直接加载 RDB 文件恢复数据。RDB 的特点是对 Redis 性能影响小，因为写盘过程在子进程完成，父进程几乎不被阻塞，但缺点是**如果 Redis 宕机，最新的数据可能丢失**，因为快照是周期性的，而不是实时的。

#### AOF 

Redis 的 AOF 持久化本质上是**命令日志机制**，它记录的是对 Redis 的每一次写操作，而不是某个时间点的内存快照。每当有写命令执行时，Redis 会把这条命令以可重放的格式追加到 AOF 文件末尾，这样就形成了一条连续的日志，记录了从启动开始对 Redis 所做的所有写操作。AOF 文件的格式是 Redis 自己定义的协议序列化形式（Redis Serialization Protocol，RESP），既包含命令名，也包含参数和过期信息，保证在重放时可以准确恢复当时的操作。写入策略可以配置成不同模式：立即同步到磁盘（保证最强一致性但慢）、每秒同步一次（折中性能和数据安全）、或者由操作系统决定缓冲刷盘（性能最好但可能丢最近一部分数据）。为了避免文件无限增大，Redis 还提供 AOF 重写机制，当文件积累到一定大小时，Redis 会在后台生成一份新的紧凑 AOF 文件，只包含重放当前内存状态所需的最小命令集合，同时继续接受客户端请求，这样既压缩了日志，又保证了数据完整性。启动 Redis 时，如果配置了 AOF，Redis 会顺序读取并重放 AOF 文件里的每条命令，从而把内存恢复到崩溃前的状态。AOF 的特点是**可靠性比 RDB 高，数据丢失窗口小**，缺点是写盘频繁和文件可能较大，对性能开销更敏感，但在追求持久化安全的场景下非常适合。

### 分布式锁

Redis 做分布式锁的核心思想是利用 **Redis 对单条命令的原子性** 来保证在分布式环境下某个资源同一时间只被一个客户端持有。当客户端想要加锁时，它会向 Redis 执行一个 SET 命令，并带上 NX（只有键不存在时才设置）和 EX（过期时间）参数，这样 Redis 会在键不存在时原子性地创建锁，并为锁设置自动过期时间，保证即使客户端宕机，锁也能自动释放。加锁成功的客户端就拥有了资源的唯一访问权，如果失败，客户端可以选择重试或等待。当客户端使用完资源后，需要释放锁，它会发送 DEL 命令删除对应的键，但为了避免误删别人持有的锁，每个锁一般会绑定一个唯一标识（比如 UUID），客户端释放前会先检查值是否和自己的一致，只有一致才删除，这样可以防止锁过期后被其他客户端重新获取时误删。为了处理多节点 Redis 的场景（例如 Redis 主从或者集群），有类似 Redlock 的算法提出：客户端需要在多个独立 Redis 节点上同时获取锁，只有当超过半数节点成功获取锁时才算加锁成功，同时设置一致的过期时间；这样可以保证在单个节点宕机或网络分区时锁的正确性。整个机制的核心是**利用 Redis 的单命令原子性、键唯一性和过期机制**，通过客户端协议保证锁的互斥性和容错性，从而实现一个可靠的分布式锁系统。

### 集群

#### 主从复制/同步

Redis 的主从复制机制是通过**一个节点作为主节点（Master），一个或多个节点作为从节点（Slave）来实现数据同步和高可用的。主节点负责处理所有写操作，同时把写命令以复制流（replication stream）的形式发送给从节点，从节点只读，不处理写请求，只负责接收并执行主节点发送的命令，从而保持数据的一致性。当一个从节点启动并连接到主节点时，它首先会向主节点发送一个同步请求，主节点会根据请求生成一个 RDB 快照，并把这个快照发送给从节点，从节点接收到快照后会加载到内存中形成自己的初始数据状态。与此同时，主节点会把在生成快照期间产生的写命令缓存在内存里，等从节点完成 RDB 加载后，这些缓存在内存中的写命令会被发送给从节点并执行，从而保证从节点能够完整追上主节点的最新状态。**这就是所谓的**全量同步加增量同步过程**。同步完成后，主节点会持续把新的写命令通过复制流发送给从节点，从节点实时执行这些命令，保证数据逐步一致。Redis 的主从复制是异步的，主节点写入不需要等待从节点确认，这样写性能不会被复制拖慢，但也意味着在主节点宕机的瞬间，最新写入的数据可能还没同步到从节点，会存在短暂的数据丢失风险。为了提高可靠性，Redis 提供了半同步机制，通过配置等待至少一个从节点确认接收到复制流后再返回写操作成功，来减少这种风险。整个主从复制的核心逻辑就是：通过初始的 RDB 快照实现从节点的全量初始化，通过持续的命令流实现增量追赶，保证主从节点的数据尽可能保持一致，同时利用异步机制最大化写入性能。

#### 哨兵模式

Redis 哨兵模式的核心是**对 Redis 主从集群进行监控、故障自动切换和配置通知**，目的是保证高可用。哨兵本身是一个独立进程，它不会存储业务数据，而是通过不断向主节点和从节点发送 PING 命令来感知节点的状态，同时也监听从节点与主节点的同步状态和响应延迟。当哨兵发现主节点在超过一定时间内无响应，并且有足够数量的哨兵确认这一状态，就认为主节点下线（subjective + objective down）。一旦确认主节点宕机，哨兵会从当前的从节点中选举出一个新的主节点，通常选择同步偏差最小、数据最完整的从节点作为新主节点，然后通知其他从节点开始复制新主节点，并通过发布配置变更通知客户端更新其连接信息，使客户端可以透明访问新主节点。哨兵之间通过投票机制协调，保证在网络分区或多哨兵部署时，只有一台从节点会被提升为主节点，从而避免脑裂和主节点冲突。整个哨兵机制的核心是持续的健康检查、基于多数投票的故障判定和自动化的主从切换，以及对客户端的配置通知，使 Redis 集群能够在主节点宕机时保持服务可用，同时尽量保证数据的一致性和最小的服务中断。

>**脑裂**本质上是分布式系统里节点对状态感知不一致导致出现**同一时间多个节点都认为自己是主节点**的情况。在 Redis 哨兵模式中，脑裂可能发生在主节点宕机或网络分区时，比如主节点与大部分从节点之间的网络断开，而少数从节点还能与一部分哨兵通信。此时各个哨兵对主节点是否下线的判断可能不一致，一部分哨兵认为主节点宕机，并尝试提升从节点为新主节点，而另一部分哨兵仍认为原主节点正常，这样就可能出现两台主节点同时对外提供写服务，导致数据冲突和不一致。为了避免脑裂，Redis 哨兵使用**多数投票机制**来判定主节点宕机，只有当超过半数哨兵确认主节点不可用时，才会执行主从切换，从节点才可能被提升为主节点；同时哨兵之间通过集群总线不断同步状态，确保不同哨兵对同一主节点的判定趋向一致。即便如此，在网络分区期间仍存在短暂的不确定性，但多数投票原则可以保证最终只有一个主节点被合法提升，从而把脑裂风险控制在可接受范围内。脑裂的本质问题是**分布式环境下节点对真实状态感知存在延迟或不一致**，而哨兵的设计通过投票、心跳、切换和通知机制，把这种风险最小化，使 Redis 集群在主节点故障时能够尽快恢复服务而不产生双主冲突。

#### 分片集群

Redis 分片集群的核心思想是**将整个 key 空间划分成固定数量的槽（slot），然后把这些槽分配给不同的节点，从而实现水平扩展**。在 Redis Cluster 中，默认将 key 空间划分为 16,384 个槽，每条 key 根据哈希算法映射到一个具体的槽，客户端访问 key 时可以根据槽计算出对应的节点，从而直接访问正确的节点而不经过中央路由。每个节点维护自己负责的槽的数据，并可以配置从节点进行异步复制以提供高可用，当某个主节点宕机时，从节点可以提升为主节点接管该槽的服务。节点之间通过集群总线交换拓扑信息，包括节点状态、槽分配和复制关系，使集群能感知故障和重新分配槽，同时客户端在访问 key 时如果连接到了错误节点，节点会返回重定向信息（MOVED 或 ASK），客户端据此去正确节点完成操作。集群在执行写操作时，节点只对自己负责的槽进行处理，写命令在主节点执行并异步复制给从节点，读操作可以选择主节点或从节点读取，保证数据访问的高效性。整个 Redis 分片集群的核心在于**哈希槽实现水平分片、节点复制保证高可用、集群总线和重定向机制保证客户端访问透明性**，从而在保证单节点高性能的前提下，实现数据的横向扩展和故障容错。

### 单线程与多路复用

Redis 之所以能够在内存数据库中实现极高的性能，核心在于**单线程模型和多路复用机制的结合**。Redis 用单线程处理所有客户端请求，这意味着每条命令在执行过程中都是原子性的，不会被其他命令打断，也不需要加锁来保护内存数据结构，从而避免了多线程环境下的锁竞争、上下文切换和缓存行抖动问题。为了弥补单线程在处理大量客户端连接时的潜在瓶颈，Redis 利用操作系统提供的多路复用 I/O 接口（如 epoll、kqueue、select/poll）建立事件循环（event loop），在一个线程中同时感知大量客户端连接的就绪状态，包括可读、可写以及定时事件。事件循环每次询问操作系统，获得所有就绪事件的列表，然后按顺序处理这些事件，使单线程在逻辑上能够同时处理成千上万的客户端请求，而不需要为每个连接创建独立线程，也不必阻塞等待网络 I/O 完成。为了保证事件循环不被耗时操作阻塞，Redis 会把一些耗时任务如 RDB 快照生成、AOF 重写、慢查询日志记录或大对象惰性删除交给后台线程或子进程处理，主线程继续响应客户端请求。这样，单线程提供了对内存操作的高效和原子性，多路复用提供了对大量连接的高并发调度能力，两者结合，使 Redis 能够在单线程模型下实现极高的吞吐量和低延迟，同时逻辑简单、可预测，保证了数据结构访问的效率和事件处理的顺序性。
